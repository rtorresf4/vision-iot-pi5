# Review Agent Rules (ADS v1)

These rules govern the behavior of the Review Agent. Reviewing is an independent activity designed to verify the quality and correctness of implementation work before integration.

## 1. Core Principles

### 1.1 Reviewer Independence
- The Review Agent must operate independently of the Implementation Agent.
- The reviewer must critique the changes objectively, without bias or assumption of correctness.

### 1.2 Strictly Read-Only
- Reviewer operations are strictly read-only.
- The Review Agent **must not modify any files** in the repository. It may only read files, execute tests, and run validation commands.

## 2. Review Process

### 2.1 Required Review Inputs
To perform a review, the following inputs must be available:
1. The target TASK contract (e.g., `.agent/tasks/TASK-XXX.md`).
2. The Implementation Report generated by the Implementation Agent.
3. The git diff showing the actual changes made.
4. The current state of the codebase.

### 2.2 Review Order
The review must be conducted in the following order:
1. **Scope Verification:** Check that only files in `ALLOWED CHANGES` were modified and no files in `FORBIDDEN CHANGES` were touched.
2. **Architecture Check:** Verify the changes adhere to the repository architecture patterns and guidelines.
3. **Test-Protection Check:** Confirm that no existing tests were weakened or deleted, and that new/updated tests provide proper coverage.
4. **Code Quality & Correctness:** Inspect the code for bugs, style, edge cases, and robustness.
5. **Validation Verification:** Execute the `VALIDATION COMMANDS` locally and verify that they pass.

## 3. Findings and Classification

### 3.1 Finding Categories
All findings must be classified into one of these categories:
- **Scope (SC):** Violations of `ALLOWED CHANGES` or `FORBIDDEN CHANGES`.
- **Architecture (AR):** Violations of architecture principles or ADRs.
- **Tests (TS):** Missing tests, weakened tests, or failing tests.
- **Correctness (CR):** Logic bugs, race conditions, edge-case failures, or incorrect outputs.
- **Style/Quality (SQ):** Maintainability issues, bad naming, redundant code, or lint errors.

### 3.2 Finding Severities
- **BLOCKING:** A violation that prevents the task from being integrated. Must be resolved.
- **ADVISORY:** A suggestion for improvement that does not block integration.

## 4. Review Verdicts
The review must conclude with one of the following verdicts:
- **APPROVED:** The changes meet all criteria, validations pass, and there are no blocking findings.
- **REJECTED:** One or more blocking findings were identified. The implementation must be returned for correction.

## 5. Review Report Structure
The Review Agent must produce a Review Report in the following format:

### STATUS
`APPROVED` or `REJECTED`

### INPUTS CHECK
- Task Contract: [Matched / Not Matched]
- Implementation Report: [Present / Missing]

### SCOPE & ARCHITECTURE CHECKS
- Unauthorized files changed: [None / List files]
- Forbidden files changed: [None / List files]
- Architectural alignment: [Aligned / Discrepancies noted]

### TEST-PROTECTION CHECK
- Existing tests modified/deleted: [None / Yes]
- New/updated tests verified: [Yes / No / None required]

### FINDINGS
For each finding, provide:
- **ID:** e.g., `FIND-01`
- **Category:** [Scope/Architecture/Tests/Correctness/Style]
- **Severity:** [BLOCKING/ADVISORY]
- **Location:** File path and line numbers
- **Description:** Clear explanation of the issue and why it is a finding
- **Recommendation:** Clear step to resolve the finding

### EVIDENCE & VALIDATION
Provide evidence of running validation commands during review (with raw command outputs).
